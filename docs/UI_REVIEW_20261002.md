# Transit PWA UIレビューと改修（2026-10-02）

## 良いUIの定義と評価方法

本アプリの主要タスクは「出発地・到着地と日時を指定し、到着時刻・料金・乗換回数を比較して経路を選ぶ」ことです。良さは装飾の好みではなく、目的の達成、必要な操作・判断の少なさ、誤操作からの回復で評価します。

認知科学は背景となる研究分野であり、実務上はHCI、ユーザビリティ、認知アクセシビリティの問題です。Nielsenの10原則とW3Cの認知アクセシビリティ指針を、このアプリのタスクに落とし込みました。これらは評価の指針であり、準拠するだけで全員にとって使いやすいと保証されるものではありません。

| 評価基準 | 改修前の観察 | 改修内容 |
| --- | --- | --- |
| 主要タスクと情報の階層が明確 | 入力・交通手段・事業者・座席・予算が同じ階層に並ぶ | 出発・到着、移動時刻、検索を基本画面に置く。詳細条件は開閉式に集約 |
| 記憶や推測に依存しない | 発/着の短縮表記。設定を隠すだけでは適用条件を忘れる | 出発/到着の常設ラベル。閉じた検索条件にも交通手段・列車・座席・予算の要約を表示 |
| 予測可能で誤操作しにくい | 現在時刻と編集可能な時刻を併記。部分一致の先頭候補に勝手に置き換えて検索 | 「今すぐ出発」では日時欄を隠し今日の現在時刻を利用。時刻指定時に日時欄を表示。部分入力は明示的な候補選択を要求 |
| 状態と回復方法が分かる | モーダル警告。結果がどの条件か分かりにくい。詳細開閉がカードへの暗黙のタップ | 入力欄の近くにエラーと修正方法。前回の検索地・日時を表示し条件変更後に再検索通知。詳細開閉に明示的なボタンと状態ラベル |
| 読めて操作できる | 候補が絶対位置で重なるため余白の手動補正が必要。経路内の途中駅はクリック可能なspan | 候補を通常フローに変更。候補の矢印キー・Enter・Escape操作。途中駅もbutton化。44px以上の主操作、文字拡大時の折り返しを改善 |

標準状態の初期画面で見える操作対象は15個から7個になります（出発・到着、経由追加、入替、時刻方式、条件開閉、検索。文字入力時に現れる消去ボタンを除く）。必要な設定自体は保持し、要約で状態を確認できます。この数は画面の整理の指標であり、認知負荷が同じ割合で減ったという意味ではありません。

## 経路結果の整理

- 比較用の先頭情報は出発・到着時刻、所要時間、乗換回数、料金、路線名を優先しました。
- 前後の便の操作は経路詳細の中へ移動しました。
- 距離は比較用の要約から外し、主要な判断情報に集中させました。
- 始発・終電の目安を結果の下に移し、選びたい経路より先に読ませない配置にしました。
- モード、並び順、経路開閉に選択状態・開閉状態を付与しました。
- バスの収録範囲と運賃の扱いを条件内で説明しました。

## 検証

Nodeの回帰テスト21件、既存の実データを使用したUI描画検証、Service Workerキャッシュ検証を実行しました。誤った候補を自動検索しないこと、現在時刻へ戻した際に未来日を残さないこと、古い結果を明示すること、開閉ラベルの整合性を追加で検証しています。

Vercelプレビューをクラウドブラウザで操作し、船橋→五反田の通常検索、上野経由の翌日09:50到着指定、到着期限を超える次の便の防止、条件変更通知、候補のキーボード選択、部分入力「しぶ」の選択要求を確認しました。ブラウザ確認で日付入力のflex-basisが縦方向に作用する問題を見つけ修正しました。

`tests/responsive-preview.html` は390px/320px/820pxと文字サイズ100%/200%で繰り返し確認するための開発用画面です。実画面をiframe内に読み込みます。端末固有のソフトウェアキーボードやスクリーンリーダーの検証は別途必要です。

## 判断と残る確認

改修前は、既にタップ領域や駅候補の改善がある一方で、情報の階層、操作の予測可能性、明示的な開閉、検索後の状態表示に問題がありました。今回、その観察可能な問題を修正しました。

認知負荷や使いやすさの最終評価には実利用者の確認が必要です。代表タスクを同条件で改修前後に試し、完了率、誤選択数、検索完了までの時間、迷った操作、使いやすさの主観評価を比べることを推奨します。今回、実利用者の比較実験やWCAG全項目への適合認証は行っていません。
